# 让工具自己写 DNS 记录（DNS-01 自动化）

> 适用范围：域名托管在阿里云云解析，需要把 DNS-01 验证里「复制 TXT 值、去控制台粘贴、等生效」这几步自动化。

本文只讲 DNS 记录这一段。签发、部署分别由 `acme_client` 与 `deploy/alb_deploy.py` 负责，三者通过 `certs/` 目录衔接。

---

## 一、自动化到什么程度

DNS-01 的验证逻辑是：CA 要求你在 `_acme-challenge.<域名>` 上放一条特定值的 TXT 记录，它查到即证明你控制该域名。

这条记录的生命周期很短——验证开始前写入，验证结束后即可删除。因此只要拿到解析服务商的 API，整段就能无人值守：

```
创建订单 → 写入 TXT → 等权威服务器可见 → 通知 CA 验证 → 清理记录 → 签发
```

工具把这一段接进了原有流程。界面上多了一个开关，命令行下是一组参数，底层是同一个实现。

**前提**：域名的 NS 记录确实指向阿里云云解析。域名注册在阿里云但 NS 指向别家（DNSPod、Cloudflare 等）时，云解析 API 看不到那些记录，需要换成对应服务商的接口。

## 二、权限

新建一个 RAM 子账号，只授予云解析的四个动作。仓库内附了策略文件 `deploy/ram-policy-dns.json`：

| 动作 | 用途 |
|---|---|
| `alidns:DescribeDomains` | 列出账号下的托管域名，用于定位记录属于哪个域 |
| `alidns:DescribeDomainRecords` | 查同名 TXT 记录，做幂等判断 |
| `alidns:AddDomainRecord` | 写入验证记录 |
| `alidns:DeleteDomainRecord` | 验证后清理 |

策略里第二条的 `Resource` 需要替换成自己的域名：

```json
"Resource": ["acs:alidns:*:<账号ID>:domain/example.com"]
```

`DescribeDomains` 是列表类查询，不支持资源粒度授权，`Resource` 只能写 `*`——这也是它单独占一条语句的原因。记录类动作可以精确到域名，因此即使这个子账号泄露，影响范围也限于该域名的解析记录。

两点必须强调：

- **不要用 `AliyunDNSFullAccess`。** 它覆盖整个账号的全部域名解析，包括线上 A 记录。为了自动加一条临时 TXT 记录而交出改全站解析的能力，不划算。
- **不要与部署凭证共用。** 部署用 `data/alb.env`，云解析用 `data/dns.env`，两个子账号、两份权限。工具默认就是这么分开的。

## 三、界面操作

「验证方式」选择 **DNS 验证** 后，下方会出现「自动写入解析记录」卡片：

1. 打开开关，填入 AccessKey ID 与 Secret；也可以勾选「使用已保存的云解析凭证」，直接复用 `data/dns.env` 里的那一份；
2. 点「验证凭证并读取域名」。这一步调用只读接口，能确认三件事：AccessKey 是否有效、权限是否齐全、域名是否真的在这个账号下。识别到的托管域名数量会直接显示出来；
3. 点「开始申请」。之后的流程与手动模式完全相同，区别在于第二步不再需要人去控制台粘贴。

进入验证页后，页面顶部会显示写入结果：

```
记录已由工具写入（example.com）。共 2 条，新增 2 条、复用已有 0 条；
验证结束后自动删除，不需要手动清理。
```

下方表格仍会列出记录名与值，供核对用——它不再是操作指引，而是明细。

「重新写入记录」用于记录被误删或中途失败后的补写；「立即清理记录」用于放弃本次申请时手动收尾。

## 四、机制

### 1. 幂等：先查后写

写入前先按主机记录名查询同名 TXT：

```
已存在同值记录 → 直接复用，不重复创建
不存在        → 新增一条
```

复用的判定依据是「值完全相同」。ACME 的 TXT 值是 token 摘要，每次申请都不同，所以正常流程下不会误判。

### 2. 生效判定：问权威服务器，不问公共 DNS

写入云解析之后，记录并不是立刻对全世界可见。递归解析器（8.8.8.8、223.5.5.5 之类）有缓存，可能有几秒到几分钟的延迟；直接查它们会得到「还没生效」的假象，也可能读到上一个值。

工具的做法是先查出该域名的权威 NS，再逐台直接向权威服务器查询 TXT，不经过任何缓存：

```
zone_of(_acme-challenge.example.com) → example.com，NS = ns1.aliyun.com…
对每台 NS 直接发 TXT 查询 → 全部返回期望值才放行
```

只有一步之遥的差别：跳过这一步直接提交验证，CA 查不到记录就会判失败，而授权一旦被判失败就无法复用，必须重新创建订单。等几十秒，比重新走一遍便宜。

等待上限默认 180 秒，超时则不提交验证，并保留已写入的记录——稍后重试即可，不必重新写。

### 3. 清理：只删自己写的

验证结束（无论成功还是失败）都会删除本次写入的记录。删除依据是记录 ID，工具只删自己创建的那些；同名下用户原有的其它 TXT 记录不受影响。

清理失败只记一条告警，不阻断签发：一条残留的验证记录不影响安全，但会污染记录列表，因此失败会在日志里标出来。

### 4. 通配符与裸域同时申请

`*.example.com` 与 `example.com` 各自有独立的授权与 token，但验证名都落在 `_acme-challenge.example.com` 上。也就是说同一个主机记录下要同时存在两条不同的 TXT。

云解析允许同名同类型的多条记录（免费版上限 10 条），工具会分别写入，并按「两条值都能查到」作为放行条件。手工操作时这一步最容易出错——先删后加就会丢掉前一条。

### 5. TTL

TXT 记录的 TTL 用 600 秒，这是免费版允许的最小值。新增记录通常立即生效；影响主要出现在删除和后续重签：被缓存过的旧值要等 TTL 过期才消失。工具用「先查后加、按 ID 删除」的方式避免制造重复记录，也避免在同一名字上反复改值。

## 五、命令行与计划任务

无人值守入口是 `issue.py`，与网页界面共用同一套逻辑：

```bash
python issue.py --domains "*.example.com,example.com" --email ops@example.com \
    --dns aliyun --access-key-id LTAI... --access-key-secret ...
```

凭证优先从参数读取，也可以放在环境变量 `ALIBABA_CLOUD_ACCESS_KEY_ID` / `ALIBABA_CLOUD_ACCESS_KEY_SECRET` 里，避免出现在命令历史与进程列表。

成功时退出码为 0，最后一行输出证书目录：

```
CERT_DIR=D:\ai\letsencrypt-tool\certs\wildcard-example.com-20270125-031500
```

失败时退出码为 1，参数错误为 2。失败会自动清理已写入的解析记录；需要保留现场时加 `--keep-records`。

接到计划任务时，签发与部署串成一条命令即可。部署脚本在不指定 `--cert-dir` 时会取 `certs/` 下最新的一版，因此不需要手工传路径：

```bash
# 每天凌晨跑一次：未到期时整条链路是空操作，到期前自动换新并替换监听证书
python issue.py --domains "*.example.com" --dns aliyun --email ops@example.com \
  && python deploy/alb_deploy.py --listener-id lsn-xxxxxxxx --region cn-hangzhou \
       --domain example.com --verify-host www.example.com
```

Windows 任务计划里把上面两行写进一个 `.bat`，触发器设为每天；Linux 用 cron：

```cron
30 3 * * * cd /opt/letsencrypt-tool && ./issue.sh >> /var/log/cert.log 2>&1
```

幂等由两层保证：签发侧同样的域名不会重复写记录（复用同值），部署侧比对本地序列号与监听上的证书 ID，两者一致就跳过。因此这条命令每天跑和不跑，结果是一样的。

## 六、排错

| 现象 | 原因 | 处理 |
|---|---|---|
| `AccessKey ID 不存在` | AK 抄错、多了空格，或不是当前账号的 | 重新复制；确认子账号属于域名所在账号 |
| `AccessKey Secret 不正确` | Secret 粘贴不全或混入空格 | 重新粘贴，注意首尾 |
| `这个 RAM 用户没有云解析权限` | 策略未附加，或语句里的域名写错 | 按第二节重新附策略 |
| `域名 xxx 不在当前账号的托管域名中` | NS 指向别家，或域名不在该账号 | 先 `nslookup -type=NS example.com` 确认 NS；或换账号 |
| `该主机记录下记录数达到上限` | 同名 TXT 堆积（多为反复调试留下） | 到控制台删掉废弃的 `_acme-challenge` 记录 |
| 日志显示已写入，但一直提示「尚未在权威服务器生效」 | NS 缓存、或写入到了错误的域 | 用 `nslookup -type=TXT _acme-challenge.example.com 8.8.8.8` 复核；确认记录所在域名与 NS 一致 |
| 验证通过但记录还在 | 清理失败（权限缺少 Delete） | 补 `alidns:DeleteDomainRecord`，或用「立即清理记录」 |

排查顺序建议：先看「验证凭证并读取域名」能否通过（这一步只读，能排除凭证与权限问题），再看写入日志，最后才看 CA 的验证结果。

## 七、边界

- **只支持 NS 指向阿里云云解析的域名。** 其它服务商需要在 `dns_providers/` 下增加实现：基类已经抽象出「列域名、查记录、增删记录」三个动作，新增一个厂商大约百来行。
- **没有做 DNS 记录的批量回滚。** 清理按记录 ID 逐条删除，中途失败会留下部分记录，日志里会列出名字。
- **凭证仍是长期密钥。** AccessKey 不像临时凭证会自动过期。若所在环境支持实例角色（ECS RAM 角色、函数计算角色），更稳妥的做法是改为从元数据服务取临时凭证，这需要按部署环境单独实现。
- **DNS-01 不是唯一解。** 如果证书就装在同一台机器上、80 端口可用，「自动 HTTP 验证」不需要任何云厂商凭证，链路更短。DNS-01 的价值在于泛域名、以及证书与站点不在同一台机器的情况。
