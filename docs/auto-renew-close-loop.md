# 从三个断点到一个闭环：证书自动签发到自动部署

> 范围：域名解析托管在阿里云、应用入口是阿里云 ALB 的场景。这篇只讲"为什么现在能全自动了"，具体参数见 `README.md` 与 `docs/` 下另外两篇。

---

## 一、之前断在哪

一张 Let's Encrypt 证书有效期 90 天。要让它一直有效，必须按顺序做完四件事：证明域名归你、拿到证书、传到用证书的地方、在到期前重来一遍。

这四件事本来都能自动化，但过去有三处必须人接手：

| 断点 | 表现 |
|---|---|
| DNS-01 验证 | 工具告诉你"去加一条 TXT 记录"，你复制值、登录控制台、粘贴、等生效、再点回来继续 |
| 证书部署 | 下载下来的 `.pem` 要手工导入 ALB，选对监听，选对证书类型 |
| 续期计时 | 90 天后的事，靠日历提醒或某天发现浏览器报错 |

三个断点，每一个都在"机器做完了、等人"的地方停下。自动化链条只要有一处需要人，整条就不是自动化，而是"辅助手工"。

---

## 二、补上的三块

**第一块：云解析接口化。** DNS-01 要的那条 TXT 记录生命周期很短——验证前写入、验证后即可删除。既然只是一条记录，就不该占用人。工具现在拿到云解析 API 权限后，自己写入、自己等权威 NS 生效、自己验证、自己删干净。界面上这一步从"复制这段值"变成了一个开关。

**第二块：部署脚本化。** `deploy/alb_deploy.py` 把"上传到 CAS、把它挂到监听上"变成一条命令，而且是幂等的——先比对监听当前证书的序列号，已经是这张就跳过，不重复上传、不产生一堆历史证书版本。

**第三块：续期判断。** 这是最容易被忽略的一块。很多人以为自动续期就是"每天跑一次签发脚本"，但那样每天都消耗一次配额，很快会撞上 Let's Encrypt 的限流。正确做法是先判断：每张证书旁边都有 `cert-info.json`，读 `not_after` 现算剩余天数，只在临期时才真的动手。

三块拼起来，配一个 Windows 计划任务，闭环就成立了：[框图](./auto-renew-close-loop.html)

## 三、闭环成立的三个条件

这一条值得单独说，因为它是这套方案唯一的适用边界：

1. **域名的 NS 指向阿里云云解析。** 域名注册在阿里云、但 NS 指向别家（DNSPod、Cloudflare），云解析 API 看不到那些记录，写入会失败。
2. **流量入口是阿里云 ALB。** 证书挂在哪里，决定部署脚本往哪写。
3. **用 DNS-01 验证。** ALB 是七层终止 TLS，证书没配好之前 80 端口的回源路径是断的，HTTP-01 在这种架构下天然别扭；泛域名更是只能用 DNS-01。

三个条件任意一个不满足，链条上就会重新出现一段等人传递的环节。

## 四、两种使用姿势

**首次给一个域名上证书**，一条命令：

```
python issue.py --domains "*.example.com,example.com" --dns aliyun --deploy --listener-id lsn-xxxxxxxx
```

下单、写 TXT、等生效、验证、落盘、清 TXT、上传 CAS、挂监听，一次走完。

**之后**，零命令。计划任务每天凌晨跑一次 `renew.bat`，绝大多数时候它只读几个 JSON、发现还有八十多天、然后退出，不发任何网络请求。进入到期前 15 天，它才真正动手。

15 天这个数字不是随手取的：它给了大约 14 次重试机会。某天机器关着、某天云解析 API 抖动、某天 ACME 服务繁忙，都不影响最终结果——第二天再来一次就行。

## 五、失败的时候会发生什么

这是自动化工具最该交代清楚的部分。

**先签后换。** 签发成功之前，线上证书一个字节都不动。签发失败，监听继续用旧证书，用户完全无感，你有 15 天时间排查。反过来"先删再传"的做法，一旦上传失败就是一段证书空窗。

**测试环境隔离。** `--staging` 签出来的证书也落在 `certs/` 下，而且到期时间可能比正式证书还晚。如果不能识别，正式证书到期时会被误判成"还有 90 天"而漏续。工具按 `cert-info.json` 里的 `directory` 字段过滤，测试产物永远不参与正式判断。

**域名集合沿用旧证书。** 续期时用旧证书的 SAN 列表下单，不会因为命令行少打了一个裸域名，导致续期后 SAN 悄悄变少、某个子站突然报证书不匹配。

**幂等。** 重复部署不会产生副作用，手工补跑也安全。

## 六、落地只需要四步

1. 建两个 RAM 子账号，分别只授予云解析权限（`deploy/ram-policy-dns.json`）和 ALB 权限（`deploy/ram-policy.json`）——签发只碰解析，部署只碰负载，出事时能一眼看出是谁干的。
2. 凭证存进 `data/dns.env` 与 `data/alb.env`，界面上填一次即可。
3. 用网页走一遍完整流程，确认证书签发并部署成功。
4. 双击 `register-task.bat` 注册计划任务。

第 4 步之后，这件事就结束了。

## 七、边界之外的剩余人工

自动化不是"再也不用管"，而是把人工从"每天可能发生"压缩到"一年一两次"：

- **域名换了服务商**——NS 一旦不指向阿里云，自动写入立刻失效，需要重新确认。
- **新增监听**——首次部署要指定一次监听 ID，之后工具会记住。
- **凭证轮换**——RAM 子账号的 AccessKey 建议定期更换，换完更新 `data/*.env` 即可，其余不用动。
- **证书版本堆积**——`certs/` 下每 90 天多一个目录，偶尔清理一次。CAS 上也可以用 `--prune-old-cert` 顺带清理旧版本。

这些都不是"缺陷"，而是任何自动化系统都有的配置面。区别在于：它们从"每次都要做"变成了"偶尔做一次"。
